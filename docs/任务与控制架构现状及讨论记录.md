# 任务与控制架构现状及讨论记录

记录日期：2026-09-19。

本记录是 2026-09-19 实现前的只读讨论快照。文中的“尚未实现”和待讨论项描述当时状态；当前代码、接口、运行命令与验证证据以 [PX4 SITL 起飞—悬停—降落测试记录](https://github.com/QU-of-boomboom/uav_ws/blob/main/sim/PX4_SITL_起飞悬停降落验证.md) 为准。

## 1. 已确定的职责边界

| 功能包 | 目标职责 |
| --- | --- |
| `uav_mission` | 决定当前任务阶段、目标以及成功、失败和取消条件 |
| `uav_control` | 封装控制通信、命令请求、状态反馈及周期 setpoint 发送 |
| `uav_vio_bridge` | 将 OpenVINS 位姿转发至 MAVROS，定位链路独立于任务控制 |
| `uav_bringup` | 组织 launch 和 YAML 配置，不实现任务或算法 |

计划中的控制调用关系：

```text
MissionNode → FlightTask → FlightControlInterface → MavrosInterface → MAVROS → PX4
```

任务层只依赖统一控制能力，不直接处理 MAVROS 或 DDS 消息。任务层更新目标，控制层持续发送目标；离散命令的请求发送与实际执行完成必须区分。

第一阶段目标是等待定位和飞控就绪、准备并进入 Offboard、解锁、起飞、悬停、降落、确认上锁及结束。具体顺序、转移条件和异常处理仍需讨论。暂不引入 `MissionExecutor`、多任务插件框架或自定义底层控制器。

### uav_control

- 当前构建目标为 `mavros_interface_node`，由 `main.cpp` 和 `mavros_interface.cpp` 组成。
- `MavrosInterface` 直接继承 `rclcpp::Node`，当前只有状态订阅和固定位置 setpoint 发布。
- 启动时读取目标与频率，默认目标为本地 ENU `(0, 0, 2)` 米，默认发布频率为 20 Hz；朝向四元数固定为单位四元数。
- `/mavros/state` 用于记录连接、模式与解锁状态，目前没有向任务层提供统一状态查询接口。
- 尚无解锁、模式切换、降落请求、位置和速度反馈、着陆状态，以及供任务动态更新目标的接口。
- `flight_control_interface.hpp` 只有空命名空间；`config/control.yaml` 为空。当前生效的配置和启动文件是 `setpoint.yaml`、`setpoint.launch.py`。
- CMake 仅构建可执行程序，未提供控制库、公共头文件安装和供任务包使用的导出目标。
- DDS 类型为不可实例化的预留类型，源文件不参与当前构建。
- **用户已删除 `src/flight_task.cpp`，本次已确认该文件不存在。** 任务职责归入 `uav_mission`，不再将此文件列为待清理项。

固定发布高度目标不代表已经实现自动起飞，也不代表飞控已经接受目标。

## 5. 下一步讨论顺序

### 先确定任务与控制如何连接

当前 `FlightTask` 的构造函数接受控制接口引用，表达的是同一进程内直接调用 C++ 对象的设计；独立的控制可执行程序本身无法通过这个引用被另一个进程直接调用。

待讨论两种方式：

| 方式 | 需要明确的内容 |
| --- | --- |
| 同一进程内装配任务与控制 | 控制实现作为库导出；谁创建并持有后端对象；ROS 回调和两个更新周期如何被驱动 |
| 独立进程，通过 ROS 接口连接 | 任务命令、目标和状态的 topic/service/action 契约；若保留 C++ 接口，谁实现通信代理 |

**讨论起点建议：优先考虑同一进程内装配。** 它贴近现有接口引用设计，第一阶段所需通信环节较少。包可以保持独立；进程组织方式无需与包一一对应。这只是待讨论建议，尚未确定实施，也尚未决定独立控制节点的最终用途。

无论采用哪种方式，都需明确控制发布的唯一所有者，避免旧固定目标节点与任务控制同时写入 setpoint。

### 再确定最小控制契约

- 状态：连接、解锁、模式、着陆状态、位置，以及定位有效性和数据新鲜度；未知状态不能默认等同于有效或已着陆。
- 命令：请求是否发出、是否被接受、实际状态是否达到，分别由谁记录与判断；超时和重试归属要清楚。
- 目标：坐标系、单位、航向，以及起飞高度是相对起飞点还是本地坐标绝对高度。
- 周期：任务更新与 setpoint 发布各由谁驱动；取消或失败后当前目标如何处置。

### 最后落实第一版状态机的规则

先定义每个阶段的进入动作、完成条件和超时处理，再讨论实现。重点包括：定位就绪如何判定、何时准备 Offboard、如何确认起飞和降落，以及取消任务时如何根据地面或空中状态处理。任务结果与飞行处置应分清，不能仅停止任务更新就假定飞机已安全结束飞行。

后续验证应逐级区分：可编译、主机任务逻辑检查、ROS 通信、PX4 SITL 飞行闭环、实机验证。当前尚未推进这些新增验证。
